# 商店截圖優化——工作理論

一個精簡的模型，說明截圖*為什麼*會轉換。蒸餾自 DesignerAnts（Teodora，做過 1,000+ 套 App Store
截圖）、《App Store Screenshot Optimization Playbook》（從她的動態整理出的 100 條做法——
需留 email 取得的 PDF，此處用我們自己的話摘要，不轉載）、Paul Solt 的〈The Screenshot Mistake
That's Costing You Downloads〉，以及 `copywriting.md` 裡的文案研究。每條原則最後都有
**→ tooling**：本工具組裡是什麼在強制或協助它。

## 0. 你在優化的漏斗

```
曝光（搜尋結果：icon + 名稱 + 前 1–3 張截圖，約 7 秒，縮圖大小）
  → 點進 → 產品頁（全尺寸輪播，一次一張）
    → 安裝
```

- 約 70% 的人不會滑過第 1 張；約 90% 在第 3 張停下。前三張決定一切；第 4 張之後是給已經被
  說服的人看的。
- 截圖**先以縮圖大小被看到**。需要放大才看得到的東西等於不存在。
- 轉換率（頁面瀏覽 → 安裝）是唯一的分數。「好看」是意見；數字不是。

→ tooling：`render.mjs --preview` 的對照圖刻意做成縮圖大小；先在那裡判斷。

## 1. 文字承擔約 70% 的效果

同樣的畫面、改寫標題：DesignerAnts 的案例裡轉換率 +80–90%。所以：

1. **先標題，後畫面。**先寫句子，再挑能證明它的畫面。
2. **結果，不是功能。**「雲端同步」→「你的筆記在每台裝置上。」一直問「所以呢？」直到它描述的是
   使用者的生活，而不是 app 的規格。
3. **≤ 8 個詞、動詞開頭、白話。**不用術語、不用文化限定的梗（「Pong」）、不用行銷陳腔
   （#1、最佳、立即下載——最後一個也會被 Apple 退件）。
4. **一張一個訊息。**標題裡有逗號或「和」就是兩張。
5. **具體勝過模糊。**「每天早上 10,000 人」> 「深受喜愛」——但只能用站得住腳、能持續更新的數字。
6. **語氣對準受眾**；整套大小寫與標點一致；校對。
7. **在地化是改寫**，預留 30% 的膨脹空間（德文 / 法文）與較短的 CJK 行。

→ tooling：`copy.<locale>.json` 每張有 `role`；`copywriting.md` §3 的 10 條檢核表；
`render.mjs` 的標題溢出檢查；`==字==` 高亮讓強調留在排版上而不是多加字。

## 2. 順序是故事，不是型錄

| # | 任務 | 為什麼在這裡 |
|---|---|---|
| 1 | **鉤子**——點出痛點或提問 | 換來那一次滑動；最常被拿來測試 |
| 2 | **改變**——對他們來說什麼不一樣了 | 承諾 |
| 3 | **證據**——數字、評分、結果視覺 | 在他們離開前消除疑慮 |
| 4–5 | 讓承諾成真的**功能** | 給還在讀的人 |
| 6+ | 反對意見（隱私、價格）、平台、第二個證據 | 選配 |

如果畫面任何順序都成立，那就是型錄。從不同角度強化核心價值，而不是羅列不相干的功能。
把社會認同放在疑慮最高點（第 3 張），不是最後。

→ tooling：`store-screenshots` §1 在拍攝前先寫序列；`store-art/references/decks/` 的 deck
示範節奏；`--strict` 拒絕標題 / 裝置互撞。

## 3. 服務文字的視覺規則

- **對比優先。**淺字配深底或深字配淺底；照片上加遮罩或陰影。郵票大小也讀得出來，否則只是裝飾。
- **在同類中突出，對品牌忠實。**如果所有競品都是藍白，暖色或霓虹就能停住滑動；必要時為行銷延伸
  app 內的調色盤。
- **真 UI，加強過。**真實畫面、最佳狀態、有企圖心但做得到的資料。裁切或放大標題在講的那一塊；
  其餘壓暗或移除。
- **最多三層**：背景 → 裝置 / 插圖 → 標題 + 一個強調元素。每多一張貼紙都要有存在的理由。
- **熟悉的線索抓眼球**：通知橫幅、徽章、對話泡泡——人們早就認得的東西。（不要逼真地仿造
  *系統* UI；Apple 會退件。）
- **留白與安全邊距**：離邊 ≥ 60 px；年齡分級徽章在第 1 張的右上、影片播放鈕在正中——文案避開兩處。
- **裝置框是選擇**，不是規定：有框給脈絡，無框給 UI 更多面積。整套裡變化裝置位置
  （出血 / 傾斜 / 漂浮 / 兩台），但永遠不變風格。
- **深 vs 淺**：深色在白底商店頁通常更跳；看 app 在哪種下最好看就選哪種，整套保持一致。
- **全景圖**獎勵滑動，但每一張都必須能獨立成立；接縫永遠不切到標題、臉或關鍵數字。

→ tooling：一套一個 `style` + 每張不同 `layout`；裝置佔比 / 重疊檢查；`references/quality-bar.md`
的構圖範圍；60 px 邊距已內建在每個風格的 `--pad`。

## 4. 合規——會讓 build 被退的事

- 秀 app 本身；不放其他 app 的畫面，不拿泛用素材圖當「截圖」。
- 不放行動呼籲（「立即下載」「安裝」），圖片裡不放「免費」這類價格宣稱，不用拿不出依據的
  「#1 / 最佳」。
- 不做逼真的假系統 UI（通知中心、系統對話框）——風格化的線索可以。
- 不誤用 Apple 裝置商標；用官方 bezel 或中性外框。
- 上傳必要尺寸（iPhone 6.9" = 1320×2868；通用 app 另加 iPad 13"）與各語系一套；截圖要跟
  上架 UI 保持同步。

→ tooling：`store-art` 附 Apple 的 bezel；尺寸是預設值；`submit-apple` / `submit-google`
載有各商店規則。

## 5. 測試、量測、迭代

- 先上一個基準，再跑 **Product Page Optimization**（App Store，最多 3 個版本）或
  **Store Listing Experiments**（Play）。**先改第一張**——它最能撼動數字。先測文案再測設計。
- 每個版本讀 2–4 週的轉換率（頁面瀏覽 → 安裝）；記錄試過什麼。隨季節或大版本更新；
  iOS / Play 每次 UI 改版後重新檢查。

→ tooling：`store-screenshots` §6；`gpc images upload --replace --confirm` /
`asc screenshots upload` 讓換版本只要一個指令。

## 一頁檢核表（印出來）

1. 拍任何畫面之前，標題已寫好並獲核可。痛點 → 改變 → 證據 → 功能。
2. 每條標題 ≤ 8 個詞、以結果表述、縮圖可讀。
3. 通過遮住 UI 測試（光靠標題就能講完故事）。
4. 一個風格、多種版面、≤ 1 個全景、第一張最強。
5. `render.mjs --strict` 全綠；對照圖以縮圖大小檢查過。
6. 沒有 Apple / Google 會退件的東西（§4）。
7. 各語系文案是改寫不是翻譯；各語系目錄分別上傳。
8. 記下日期；30 天後重讀轉換率；第一張的變體已排進隊列。
